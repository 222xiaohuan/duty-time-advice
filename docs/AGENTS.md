# AGENTS.md | Duty Time Advice Demo 开发规范

> 目标：交付可演示的排班时间报备 Demo，并保留标准产品扩展说明；不做生产级高并发、真实消息、审批、场地或特殊日期差异化。

## 1. 权威文档规则

`docs/prd.md` 是唯一需求读写入口，后续开发、评审、测试和实现都直接读取和更新该文件。Word PRD `docs/Duty Time Advice prd V1.docx` 是需求来源和归档材料；需求已经整理进 `prd.md` 后，不再把 Word 文档作为日常开发输入。数据结构目标读取 `docs/db-schema.md`，开发顺序读取 `docs/TASKS.md`，实现状态以代码为准；若实现与需求冲突，先按 `prd.md` 修正实现或提出明确冲突。

## 2. 强制术语

1. 英文统一使用 `Rosterability`。
2. Demo 状态编码使用 `ROSTERABLE`、`UNROSTERABLE`、`PRIORITY_ROSTERABLE`；`STANDBY` 仅作标准产品预留。`PRIORITY_ROSTERABLE` 受组织级优先排班开关控制。
3. 中文统一使用“可排”、“不可排”和“可排性”。
4. `locked` 是只读标记，不得作为可排性状态或覆盖原状态。
5. 不得擅自新增业务枚举、状态编码或字段。

## 3. Demo 业务边界

1. 角色使用 Mock `admin / manager / employee`。
2. 模板按周一至周日维护，只按组织、员工类型和岗位匹配。
3. Demo 不运行定时生成；管理员配置每个组织与员工类型的手动生成周数（1 至 12），经理点击生成按钮后，按所辖员工实际匹配的周模板生成未来完整周记录。定时开关固定关闭，星期与时间字段保留预留。
4. 跨午夜记录归属开始日期。
5. 提前锁定按香港自然日计算；`cutoff_days=N` 时，从香港今天开始连续锁定 N 天（包含当天），过去日期始终只读，截止窗口外的未来日期可编辑。
6. 创建或修改 `UNROSTERABLE` 时，同员工同业务日存在时长大于 0 的模拟班次必须禁止保存。
7. 导入导出仅做界面按钮和未开放提示，不开发文件处理。
8. 消息提醒只保留正式产品对接独立消息模块的说明，不开发发送逻辑。
9. `field_site_enable`、`enable_approval`、`special_tag_diff_enable` 必须保留，Demo 固定关闭且不执行业务逻辑。
10. Demo 不建日期标签主数据；正式产品如需时对接公司标准日历设置。

## 4. 编码规范

1. 枚举统一放在后端 `src/types/enums.ts`，前端保持同编码定义。
2. API 返回统一为 `{code:number,msg:string,data:T}`。
3. 软删除查询默认带 `is_deleted=0`。
4. Demo 不实现审计/操作日志；标准产品保留审计字段、变更快照和查询能力的扩展说明。
5. 核心规则必须有自动化测试，不得只在前端校验。
6. 数据库为本地 SQLite，ID 使用自增整数，业务日期用 `YYYY-MM-DD` 字符串、日内时间用 `HH:mm` 字符串；JSON 输出时日期统一为 ISO 字符串。

## 5. 会话与进度协议

1. 每轮开工前读取本文档和 `TASKS.md`，复述当前任务及验收标准，等待用户确认。
2. 一次只交付一条任务，不跳过前置任务。
3. 每轮结束前更新 `TASKS.md` 中的状态与 `PROGRESS` 段落，不再使用独立 `PROGRESS.md`。
4. 每产生一项可交付进展（代码、文档、配置、验证或提交）都要立即同步 `TASKS.md` 的任务状态和 `PROGRESS` 段落；记录完成内容、当前任务、阻塞点、下一步和对应提交号（如已提交），不得等到整轮工作结束后集中补记。
5. 本地 SQLite 的迁移和种子可直接执行；若后续改连任何共享或内网数据库，迁移、写入和种子操作必须先经用户确认目标环境。

## 6. 禁止行为

- 不得跳过后端校验只做页面限制。
- 不得把锁定标记实现为覆盖原可排性状态。
- 不得实现本期边界之外的导入导出、消息、审批、场地和特殊日期逻辑。
- 不得将数据库密码、连接串或其他秘密写入日志、文档、测试或版本库。
